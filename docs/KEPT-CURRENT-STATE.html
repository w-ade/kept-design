1. Executive summary

One sentence

Kept is an invite-only, single-owner library for collecting, annotating and retrieving visual references (images), that can publish a collection as an unlisted read-only "board".

One paragraph

Kept ("A library you can actually operate.") is a personal reference database. You upload images into named collections; each image becomes a Reference that carries a title, free-form notes, tags, numbered pins placed on the image with captions, and the file's facts (name, type, pixel size, bytes, source URL). You browse a collection as a grid or list, step through references with the keyboard, search across titles, notes, tags, source, file name and pin captions, and can publish any collection as an unlisted board at /m/<token> that anyone with the link can view without signing in. The product is deliberately quiet and typographic (a black-and-white look modeled on the base-ui.com homepage). Today it exists as a complete Vite + React web front end whose data layer is entirely mocked in the browser; the owner is about to connect it to Supabase and, in parallel, build a native iOS app.

Problem it solves

Stated in the repo README/plan: collecting visual references is easy, retrieving them later is not. The stated success measure is retrieval ("Retrieval is the measure of success" — earlier product principles). Kept is meant to be a structured system rather than a moodboard canvas or a pile of files.

Who it is for

  • Current reality: one person — the owner (username wade in the mock). Accounts are "let in by hand"; there is a public "Request an invite" form, but requests only land in the requester's own browser (mock). Team/multi-user ACLs are explicitly out of scope for v0.
  • Intended: designers / visual thinkers who keep inspiration and reference images; the landing page says nothing more specific. Beyond "invite-only early development" the target audience and business model are Unknown / not yet decided.

What makes it different (as the project frames it)

  • It is a library you operate (a "Drive job" in the v0 spec's words: collections, references, inspector, search), with the Reference as the unit of meaning — not a canvas and not a social feed.
  • Sharing is a surface, not the home. Boards are a secondary, unlisted, read-only publishing feature.
  • Privacy and ownership by default: private storage, invite-only, planned two-factor required on every row (AAL2), no public gallery, no SEO index.
  • Deliberately plain UI (no filled buttons, one grey scale, one accent color used only for errors).

Nothing in the repo yet demonstrates a technical differentiator (no OCR, no semantic search, no AI). Differentiation today is product framing and UI craft.

What Kept is NOT

  • Not a canvas-first moodboard tool (earlier README: "not just a canvas for temporarily arranging images").
  • Not a public gallery or social network. No public board index, no discovery.
  • Not a multi-user/team product in v0.
  • Not currently a desktop app, and not (yet) a mobile app.
  • Not an AI product today. No AI feature exists in code.
  • Not a Next.js app, and not using shadcn/MUI/Tailwind (explicitly excluded in the v0 spec).
  • Not a Capacitor/web-view wrapper on iOS — that plan was abandoned (see section 2).

3. Product thesis

Core idea

Collect visual references once, give them structure and personal meaning, and reliably find them again. From the v0 spec: "You still operate a library (Drive job, Reference as the unit)." Sharing a collection as a beautiful unlisted board is a side effect of having organized it, not the point.

Product principles (from earlier README; still the reference text)

  1. Capture should be effortless; add structure progressively.
  2. Context is personal; the owner's interpretation is as valuable as source metadata.
  3. Structure should be layered (tags, collections, notes, later relationships).
  4. Retrieval is the measure of success.
  5. Relationships should be explicit (deferred).
  6. Local ownership matters (partly superseded by cloud Supabase storage; see Open Questions).
  7. The interface can be spatial without the product being canvas-first.

Design principles (from kept-ui.html)

  • "Strip things down before adding anything." Modeled on the base-ui.com homepage, not its docs.
  • Plain text links, hairline-ruled lists, no filled buttons, sentence case, weight 400 everywhere.
  • Only Base UI (@base-ui/react) for interactive primitives; layout in custom CSS.
  • CSS-only motion in v0, honoring prefers-reduced-motion.
  • Four shells only (Marketing, Auth, App, Board). "No dashboard layout."

Mental model

You (username + password + 2FA, planned)
 └─ Library
     └─ Collection            (a named group; the tile on /library)
         └─ Reference         (the unit of meaning: title, notes, tags, pins)
             └─ Asset         (the file: name, type, pixel size, bytes)  1 per reference in v0
         └─ Share             (optional: publishes the collection at /m/<token>)

Primary workflow

Capture (upload images) → Index (title, tags) → Annotate (notes, pins) → Organize (collections) → Query (search) → Retrieve (grid/list/reference page) → Share (board). "Connect" is the seventh landing-page action but is not built.

Why not Pinterest, Raindrop, Photos, Finder, Dropbox, Notion, Eagle?

Unknown / not written down. The repo and planning docs contain no explicit competitive comparison. What can be inferred from the docs: Kept positions itself as private, operable, structured, and image-first, with pins as on-image annotation and unlisted boards for sharing (vs. Pinterest's public discovery; vs. Finder/Dropbox's lack of per-image meaning; vs. Raindrop's link focus). Eagle is the closest analogue and is not mentioned anywhere. Treat this as an assumption.

Strongest differentiator

Today: the operable, private library with on-image pins and quiet UI. Planned: the iOS share-extension capture path. AI is not a differentiator (none exists).

4.2 Two-factor

/login/mfa is a placeholder: a "Continue to library" button that calls completeMfaForLab(). The real screen (QR enrollment, six-digit code) must first be designed in kept-ui (KEPT-14, todo/backlog). A session at aal1 is redirected here by the gate.

4.3 Request an invite

Public form at /request: Name (required), Email (required), "What would you keep?" (optional, ≤500 chars). Simulated 600 ms delay; dedupes by email in the visitor's own localStorage; shows "You're on the list." or "You're already on the list." The owner receives nothing today (KEPT-26/27 planned: invite_requests table + notification).

4.4 Create a collection

On /library: "New collection +" opens a dialog (Name ≤80 chars, Cancel, Create ›). Slug derived from name (lowercased, hyphenated, de-duplicated with -2, -3). Stored in localStorage key kept.lab.created.v1. The new tile fades in. Collections have a growing-textarea description ("What is this collection for?") saved in localStorage.

4.5 Upload / import images

ItemDetail
Trigger"Add images +" on a collection page.
StepsDialog → "Choose images" (multi-select phone picker) or drag-and-drop on desktop → per-file rows.
System behaviorprepareUpload decodes with EXIF orientation applied (createImageBitmap fallback to Image), redraws on a canvas to a 1600px full and a 480px thumbnail (JPEG quality 0.82) which strips all metadata (camera, location), then stores both Blobs plus facts in IndexedDB (kept-lab / uploads). One file at a time; status Waiting → Adding… → Added, or "Couldn't read this file"; "Adding 3 of 12…". Title defaults to the file name without extension.
ResultNew references at the top of the collection; collection updatedAt bumped.
Edge casesRecognized types HEIC/HEIF/AVIF/WebP/GIF/PNG/JPEG by MIME, else extension ≤5 chars, else "Image" (whether the browser can decode HEIC is browser dependent; Unknown). One failure does not stop the batch. Uploads exist only in that browser profile.
StatusWorks (mock, device-local). Real: Supabase Storage (KEPT-21). No dedupe, no size limit in the client (planned bucket limit 10 MB, KEPT-10).

4.8 Search and "All references"

See section 10. /library also has an "All references" section (Grid/List + search) that shows every reference across collections with the collection name as the second line.

4.9 Publish a collection as a board

ItemDetail
StepsCollection page Share line "Not shared. Share as a board ›" → dialog → Publish ›. Published state shows the link, Copy (→ "Copied"; falls back on plain http), publish date, "New link" (rotates the token; old link dies immediately), "Unpublish" (poppy), "Open board ›", Done. Edge casesBecause shares live in the owner's browser, a copied link works only in a browser that has that localStorage (i.e. it does not truly work for outside viewers today). A real backend is required (KEPT-23/24).

4.10 View a board (anyone with the link)

/m/:token: no header, no nav, no sign-in. Shows the collection name, "Kept by wade · N references · Published …", the description (line breaks preserved), a full-bleed grid (2/3/4/5 across) and a lightbox with arrow-key navigation. Invalid or unpublished token → error state on the same route. Footer: "Made with KEPT, a library you can actually operate." Built (mock).

  id: string; collectionId: string; title: string;

  addedAt: string;
  captureUrl: string | null;  // where captured from; null = uploaded from disk
  fileName: string; fileType: string; width: number; height: number; bytes: number;
  imageUrl?: string; thumbUrl?: string;
}
interface Share { token: string; owner: string; publishedAt: string }
interface Board { collection: Collection; references: Reference[]; share: Share }

interface KeptSession { username: string; aal: 'aal1' | 'aal2' }   // session.ts

The comment in code: "A Reference is the unit of meaning; its file (the Asset) carries the file facts. v0 has one asset per reference." There is no separate Asset or Tag or Note type in code; those are flattened into Reference. Notes are one text field, tags a string array.

10. Search

Current implementation

  • Client-side substring filter in ReferenceBrowser over the already-loaded reference list. Roadmap KEPT-22: "instant at this size" (160 references).
  • Verified in ReferenceBrowser.tsx: the query is lowercased and matched as a substring against title, the second-line meta (source site or collection name), source label, file name, notes, every tag, and every pin caption, joined into one string. Any-order multi-word queries are not supported (whole query must appear as one substring).
  • Collection search on /library filters tiles by name ("No collections match “…”").
  • "All references" search spans every collection.

Not present

Ranking, typo tolerance, saved searches, filters (by tag, date, type), OCR text, semantic search, visual similarity, embeddings, a global command palette. None exist in code.

Planned

  • KEPT-34 (later, 5 pts): server-side search and command palette (Base UI Combobox). Groundwork: a generated search tsvector column on refs.
  • v0 spec: "one SQL function over reference title/description/notes/tags/annotation captions"; "No OCR, no embeddings yet". Explicitly out until later: OCR, pgvector.
  • KEPT-52: on-device search on iOS (backlog).
  • /todo suggestions (not committed): color palettes and filter by color, smart collections (saved searches), duplicate detection, keyboard-first ("/ to search, J/K").

Known limitations

Search only sees data loaded in the browser; will not scale beyond a library that fits in memory; not accent/case-tuned beyond simple substring (Unknown).

13. Storage / file handling

Current

  • Seed images: two collections' JPEGs committed to git and served statically from public/collections/<collection>/{full,thumb}/NNN.jpg. moode-matcha: 160 references (added 2026-09-18). oklab-squares: 5 references (added 2026-09-20). Manifests in src/kept/data/*.json hold file name, type, width, height, bytes.
  • User uploads: IndexedDB DB kept-lab, store uploads (keyPath id), each record holds full Blob, thumb Blob, and facts. Never leaves the device/browser profile.
  • Sizes: full = long edge ≤1600px, thumb = ≤480px, both JPEG q0.82, metadata stripped by canvas redraw. Originals are not kept: the original file's bytes are recorded as bytes but the original is discarded.
  • Supported types (recognized): JPEG, PNG, WebP, GIF, HEIC, HEIF, AVIF (subject to browser decode). No PDF, video, SVG handling.
  • No dedupe, no deletion of references or uploads, no cache layer beyond the browser's.
  • Object URLs (URL.createObjectURL) are created per upload at load and not explicitly revoked (Unknown impact).

Planned (KEPT-10, 19, 21)

  • Supabase Storage private bucket kept-assets; 10 MB limit; allowed image/jpeg|png|webp; keys <owner_id>/<ref_id>/full.jpg and thumb.jpg; storage policies require owner folder match and AAL2.
  • Library images via signed URLs, batched. Board images via short-lived signed URLs from the board Edge Function (D-2 open; recommended signed over public copies).
  • Keep client-side resize; per-file failure cleanup (delete rows and objects on failure).
  • Seed moode-matcha into Storage (KEPT-28), then possibly remove public/collections/ from git (D-5, open; images remain in history and the repo is public).
  • R2 as a later cost escape hatch (KEPT-36).
  • Deletion behavior: Unknown / not yet decided for references; account deletion (including data) is required for App Store (KEPT-62) but design is undecided.

Privacy note: the 160 moode-matcha images are already public on GitHub in the repo's history and main; whether they are the owner's own or third-party images is Unknown.

14. Auth / security / privacy

Current (mock)

  • Invite-only in the product copy; single hard-coded lab account (wade; the password is in session.ts, committed publicly — it is explicitly a lab mock, not a real credential).
  • Session in sessionStorage (so a refresh mid-2FA stays on /login/mfa) with memory fallback.
  • Route gate useAuthGate in KeptApp.tsx is purely client-side. Anyone can read the gate's logic and the mock data; nothing is protected.
  • Public repo: AGENTS.md says no personal data, home paths or credentials; a LAN IP currently sits in KeptIos.tsx.

Planned

  • Supabase Auth: password + TOTP MFA; sign-up disabled; owner account created by hand (KEPT-16).
  • RLS is the whole security model because the browser talks straight to Postgres. One permissive policy per table (owner_id = auth.uid()) plus one restrictive policy requiring (auth.jwt() ->> 'aal') = 'aal2'. Storage policies likewise. Signed-out access only via SECURITY DEFINER functions with narrow return shapes.
  • Only the Supabase publishable key may appear in client code (VITE_ vars); service-role key only in Edge Function secrets/local seed script; never committed.
  • Board tokens: unguessable (10 chars base-36 in the mock), rotatable, unpublish immediate for new visits; signed URLs expire (~1 hour). No public gallery, no SEO indexing.
  • Username sign-in: D-1 open (recommended Edge Function; alternatives: synthetic emails, public lookup RPC which would allow username enumeration — "not recommended").
  • iOS: refresh tokens in Keychain via expo-secure-store (D-10 decided); account deletion in-app and privacy manifest are App Store requirements (KEPT-62/63).
  • Dashboard: separate Vercel project with Vercel Authentication; repo is public so anything written into it is world-readable regardless.

23. Final handoff summary — if you only read one section

What Kept is. A private, invite-only, single-owner library for visual references: collections of images, each with notes, tags and on-image pins, searchable, and publishable as an unlisted read-only board. "A library you can actually operate."

What changed most recently (2026-09-18 → 09-20). (1) The web UI was rebuilt from the kept-ui lab and declared pixel-complete. (2) The plan for iOS flipped from a Capacitor web-view wrapper to a native rebuild; the roadmap records React Native + Expo as decided, but a same-day analysis argues for SwiftUI and the two are unreconciled. (3) The roadmap grew from 37 backend issues to 72 (240 points, 12 phases) with iOS interleaved. (4) An internal dashboard (Overview, Roadmap, Decisions, Screens, Notes, Bookmarks) was added and kept separate from the product.

Most important current feature. The Reference page and its pin/note/tag annotation model, inside a library you can browse and search. Most important planned feature: the iOS Share-to-Kept extension with a background upload queue.

Most important unresolved question. Which native iOS stack (D-6/D-8: React Native + Expo recorded; SwiftUI argued). Four of twelve roadmap phases depend on it, and it also controls D-8/D-10 and the app name/bundle identifier (D-7). Six of ten decisions (D-1, 2, 3, 4, 5, 7) are open.

What is actually built today. A complete, polished web front end (16 routes and states) running on browser-only mock data: mock auth, collections, uploads (IndexedDB), notes/tags/pins (localStorage), boards (localStorage), two seeded image collections (160 + 5). No backend, no Supabase code, no real accounts, no real sharing, no search beyond client-side text, no AI, no tests, no iOS app.

What to understand before making further product decisions.

  • Nothing persists or shares beyond one browser until Supabase is built. "Built" in the feature list means built on mocks.
  • The src/kept code is synced from a separate lab repo and will be overwritten by the sync script until KEPT-6 is done; do not put backend code in synced files.
  • Do not invent screens here; new UI is designed in kept-ui first and approved before syncing (AGENTS.md).
  • The repo is public: no secrets, personal data or home paths. The 160 seed images and a LAN IP are already in it.
  • Pushing main deploys production; the owner asks for commits and pushes explicitly. The current branch is not on main.
  • AGENTS.md, the /ios page and the roadmap artifact's Overview text are stale in specific, known ways (sections 8 and 21).
  • AI/OCR/semantic search are not part of the plan yet; do not assume them.
  • Do not assume older framing (canvas-first, graph/Connect, Capacitor, kept-ui as sole UI source of truth) is still current.

End of briefing. Gaps flagged "Unknown / not yet decided" are deliberate; they were not invented.
